# Правила распределения и принятые допущения

Документ описывает, что именно делает скрипт навыка `logist-distribution`.
Все решения о статусе ФУЛ, группе и логисте принимает детерминированный скрипт;
языковая модель только запускает его и пересказывает результат.

Обозначения: **[БТ]** — правило из бизнес-требований, **[Д-N]** — наше допущение
до ответа заказчика (полный список вопросов — в [questions.md](questions.md)).

---

## 1. Входные данные

| Файл | Как распознаётся | Ключевые колонки |
|---|---|---|
| Выгрузка ФУЛ (1С) | по набору заголовков, а не по имени файла/листа | Дата, Cut-off date, Номер, Статус, Комментарий, Способ доставки, Бизнес единица, Логист, Контрагент, Страна |
| Реестр Cloud | то же | Заказ, Поставщик, Бренд, Логист, Статус, Дата подтверждения, Cut-off, Дата получения УЛ, Страна отправления, Способ доставки, Документы получены, Комментарий |
| Сотрудники (1С) | то же | Наименование, Текущее состояние, Должность, Код |

**Устойчивость к формату** [БТ]:
- колонки ищутся по заголовкам (с синонимами, без учёта регистра, пробелов, `ё/е` и знаков),
  порядок колонок и лишние колонки не важны;
- строка заголовков ищется в первых 30 строках листа (над таблицей может быть шапка отчёта);
- лист выбирается по содержимому: имя листа не важно;
- роль файла (ФУЛ / Cloud / Сотрудники) определяется по заголовкам, поэтому файлы
  можно приложить в любом порядке и с любыми именами; поддерживается и одна книга
  с тремя листами;
- `.xlsx`/`.xlsm` читаются через `openpyxl`, `.xls` — через `xlrd`.

Если обязательная колонка не найдена, скрипт не угадывает: он завершает работу
с понятной ошибкой «в файле X не найдена колонка Y, найдены: …».

## 2. Нормализация

| Что | Правило |
|---|---|
| **Номер заказа** | из «Комментария» ФУЛ по шаблону `S` + 7 цифр (`Номер: S0001234 от ДД.ММ.ГГГГ`); кириллическая `С` → латинская `S`, регистр и пробел внутри (`s 0001234`) допускаются. В Cloud номер нормализуется так же. Нет номера или найдено **несколько разных** номеров → «не определено». |
| **Поставщик** | ключ сравнения: регистр, `ё→е`, кавычки и знаки препинания убираются, пробелы схлопываются, правовые формы (`ООО`, `Co., Ltd`, `Limited`, `LLC`, `Inc` …) отбрасываются. В строку Cloud пишется написание **из реестра Cloud**, если поставщик там уже есть, иначе — из 1С (обрезанное). Похожие, но не совпавшие названия (сходство ≥ 0.88) не склеиваются, а выводятся в «Требует внимания». |
| **Способ доставки** | `air` (+ `авиа`, `avia`), `sea` (`море`), `truck`, `direct truck`, `railway` (`rail`, `ж/д`). Пусто → «не определено». Незнакомое значение → «не определено» + «Требует внимания» [Д-6]. |
| **Страна** | справочник `references/countries.json`. Китай = `Китай`, `КНР`, `China`, `CN`, `PRC` **и Гонконг** (`Гонконг`, `Hong Kong`, `HK`, `Hong Kong SAR`) [БТ]. Тайвань и Макао Китаем не считаются [Д-5]. |
| **Даты** | Excel-даты, `ДД.ММ.ГГГГ [ЧЧ:ММ[:СС]]`, ISO, серийные номера Excel. Нераспознанная дата → «не определено». |
| **ФИО и короткие имена** | см. раздел 5. |

## 3. Статус каждого ФУЛ

ФУЛ обрабатываются в детерминированном порядке: по дате ФУЛ, затем по номеру
упаковочного листа, затем по номеру строки в файле.

```
для каждого ФУЛ:
  если нет номера заказа (или их несколько)        → НЕТ_ЗАКАЗА: строка не создаётся, «Требует внимания»
  если номер УЛ + заказ уже встречались в пачке    → ТЕХ_ДУБЛЬ: та же строка выгрузки дважды, игнорируется (журнал) [Д-3]
  если заказ есть в Cloud                           → ПОВТОР_CLOUD: строка не создаётся,
                                                       комментарий «Повторная отправка ФУЛа, ДД.ММ.ГГГГ»
  если заказ уже был выше в этой пачке              → ПОВТОР_В_ПАЧКЕ: строка не создаётся,
                                                       комментарий дописывается к новой строке первого ФУЛ [Д-2]
  если дата ФУЛ < даты последней записи Cloud       → ВОЗМОЖНЫЙ_ПРОПУСК: в новые строки не попадает,
                                                       лист «Возможные пропуски» с предложенной группой и логистом [Д-1]
  иначе                                             → НОВЫЙ: группа и логист (разделы 4–6)
```

- «Последняя запись Cloud» = максимальная «Дата получения УЛ» в реестре; сравнение по дате
  без времени, ФУЛ того же дня пропуском не считается [Д-1].
- Дата в комментарии о повторе — дата ФУЛ (из колонки «Дата»), формат `ДД.ММ.ГГГГ` [БТ].
- Несколько повторов одного заказа в пачке → все даты через `; ` в одном комментарии.
- Если у строки Cloud уже есть комментарий, новый дописывается через `; ` [Д-4].

## 4. Группа логистов [БТ]

| Способ доставки | Страна отправления | Группа |
|---|---|---|
| `air` | любая, в т.ч. пустая | Авиаперевозки |
| не `air` | Китай / Гонконг | ВЭД |
| не `air` | другая страна | Мультимодальные перевозки |
| не `air` | **пусто / нераспознана** | **не определено** |
| пусто / нераспознан | любая | **не определено** |

Заметьте: для `air` страна не нужна, поэтому авиазаказ без страны распределяется,
а в колонку «Страна отправления» пишется «не определено» и ФУЛ попадает в «Требует внимания».

Если группа «не определено», строка Cloud создаётся (заказ известен), логист = «не определено»,
причина — в журнале и в «Требует внимания» (приоритет «Срочно»). В другую группу заказ **никогда не передаётся** [БТ].

## 5. Сотрудники и сопоставление имён

**Группа сотрудника** — по должности (`references/rules.json`):
`авиа…` → Авиаперевозки, `ВЭД` → ВЭД, `мультимодал…` → Мультимодальные.
**Не распределяют заказы**: ассистенты/помощники, руководители/начальники/заместители,
а также должности, не попавшие ни в одну группу [БТ].

**Доступность**: доступен только «Работает». Любой вид отпуска, «Уволен» и
**любое незнакомое состояние** (больничный, командировка, пусто) → недоступен,
причина пишется в журнал [Д-7].

**Сопоставление Cloud ↔ 1С** [БТ]: в Cloud логист записан коротко
(`Иванова Е.`, `Иванова Е.А.`, `Е. Иванова`, `Иванова`, `иванова елена`).
Имя разбирается на фамилию и инициалы; кандидат из 1С подходит, если совпадает фамилия
(без регистра, `ё/е`) и все указанные инициалы. Ровно один кандидат → сопоставлено.
Несколько кандидатов → «неоднозначно»: история и загрузка по этой записи не засчитываются
никому, имя выводится в «Требует внимания» [Д-8]. Ни одного → сотрудник не в списке
(например, давно уволен) — запись игнорируется в загрузке.

В новую строку Cloud логист пишется **в том же формате, что уже используется в Cloud
для этого сотрудника**; если его там ещё нет — в преобладающем формате реестра
(`Фамилия И.` или `Фамилия И.О.`) [Д-9].

---

## 6. Выбор логиста

Кандидаты = сотрудники целевой группы, кроме ассистентов и руководителей.

```
1. Закрепление в пачке [БТ]: если этому поставщику в этой группе уже назначен
   логист в текущей пачке → тот же логист («один поставщик — один логист»).
2. История: по реестру Cloud (все статусы) считаем, сколько заказов поставщика вёл
   каждый кандидат группы. Предпочтительный = максимум.
   Ничья по истории → у кого позже последний заказ поставщика → меньше загрузка → ФИО → Код [Д-14].
3. Если предпочтительный доступен → назначаем его («история»).
4. Если поставщик новый (нет истории в группе) или предпочтительный недоступен
   → наименее загруженный доступный кандидат группы [БТ], а не второй по истории [Д-13].
   Ничья по загрузке → меньше назначений в этой пачке → ФИО (алфавит) → Код.
5. Нет ни одного доступного → логист «не определено», «Требует внимания» [БТ].
```

**Загрузка** = число заказов логиста в Cloud со статусом «в работе»
**плюс заказы, назначенные ему в этой пачке** (иначе вся пачка новых поставщиков уйдёт
одному человеку) [Д-10].

Поставщик с заказами в **разных группах** в одной пачке (например, `air` и `sea`):
правило «один поставщик — один логист» применяется внутри группы, а сам случай
выводится в «Требует внимания» [Д-11].

Каждое назначение сопровождается обоснованием, например:

> Петрова А.: вела 4 из 5 заказов поставщика «Sunrise Textile» (история), работает, в работе 3.
> Предпочтительный Иванов С. — в отпуске, назначен наименее загруженный: Петрова А. (в работе 2; кандидаты: Петрова 2, Смирнов 5).

## 7. Форма новой строки Cloud

Порядок и названия 12 колонок берутся **из приложенного реестра Cloud** (как в файле
заказчика), значения:

| Колонка | Значение |
|---|---|
| Заказ | номер из комментария ФУЛ |
| Поставщик | написание из Cloud, если поставщик известен, иначе из 1С |
| Бренд | «Бизнес единица» из 1С |
| Логист | выбранный логист в формате Cloud или «не определено» |
| Статус | `в работе` [Д-12] |
| Дата подтверждения | пусто (заполняется при подтверждении) |
| Cut-off | из 1С как есть [БТ] |
| Дата получения УЛ | дата ФУЛ |
| Страна отправления | из 1С |
| Способ доставки | из 1С |
| Документы получены | пусто |
| Комментарий | пусто или «Повторная отправка ФУЛа, …» при повторе внутри пачки |

Любое отсутствующее во входных данных значение = **«не определено»**, без подстановок.

## 8. Результат

Excel-файл `distribution_result.xlsx`:

| Лист | Содержимое |
|---|---|
| Сводка | счётчики, какие файлы, листы и строки заголовков распознаны, предупреждения |
| Новые строки Cloud | ровно 12 колонок по форме реестра (названия и порядок — как в приложенном Cloud) |
| Повторные отправки | заказ, строка Cloud, текущий и итоговый комментарий, что дописать |
| Возможные пропуски | ФУЛ старше последней записи Cloud + предложенные группа и логист |
| Требует внимания | приоритет («Срочно» — строка не создана или логист не назначен; «Проверить»), что не так, что сделать |
| Письма логистам | черновик письма каждому логисту с новыми заказами: заказы, почему именно он (правило распределения), повторные ФУЛ по заказам, которые он ведёт; подпись — заглушка `[подпись]`, письма не отправляются |
| Журнал решений | по строке на каждый ФУЛ: статус, группа, логист, правило, обоснование, кандидаты группы с загрузкой |
| Сотрудники | как агент понял список: группа, распределяет ли заказы, доступность, имя в Cloud, загрузка |

Плюс `chat_message.txt` — готовый короткий ответ в чат (модель копирует его дословно)
и `summary.json` — сводка для модели (счётчики, «Требует внимания», обоснования).

Повторный запуск на тех же файлах даёт то же содержимое листов: в файле нет текущего
времени и случайности, все сортировки и ничьи разрешаются детерминированно.
